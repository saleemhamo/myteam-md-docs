# Example engineering team

This is a synthetic example of the proposed MyTeam.md team-definition format. It is not an executable configuration, and no runtime automatically loads it today.

## Purpose

Build and maintain an example web product. Deliver small, verified improvements and preserve clear ownership of tasks and decisions.

## Team

| Member | Responsibility | Preferred runtime |
| --- | --- | --- |
| lead | Technical decisions and delivery coordination | Selected runtime |
| engineer | Implementation and regression evidence | Selected runtime |
| qa | Independent acceptance review | Selected runtime |

All roles can use the same runtime in separate sessions, or the team can mix runtimes. Runtime and model selection are separate choices.

## Context sources

- Product overview: select during onboarding.
- Repository roots: select during onboarding.
- Engineering standards: select the repository guidance and relevant source documents.
- Internal board: select or initialize a Backlog.md project.
- Skills: select installed, applicable workflows during onboarding.

Keep exact local paths, connected account identifiers, and session bindings in the private workspace profile.

## Working agreements

- Assign one accountable engineer to each task.
- Record acceptance criteria and dependencies before implementation.
- Keep task status separate from observed session activity.
- Record reviews and verification against the inspected version.
- Escalate decisions outside the agreed scope or authority.
- Apply the target repository's instructions and the user's publishing permissions.

## Optional roles

Add delivery coordination, backend, full-stack, AI and ML, applied research, security, or reliability specialists when the work needs them.

## Reporting

Record meaningful progress and blockers. Agree any recurring checkpoint before enabling it. Keep credentials and raw session history outside this definition.
